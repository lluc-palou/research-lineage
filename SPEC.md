# Report-Decision Framework — Specification

Version 0.1.0. This document is the canonical definition of the framework. Everything else (the skill, the per-project scaffolds) is generated from it, not the other way around.

## 1. Purpose

Links three things that normally drift apart during a data science project: the conceptual guide (what the system is), the decision trail (why it changed), and the repo history (what code resulted). The report is the entry point for understanding a project; the decision log is the entry point for understanding a change; git is the immutable ledger both refer back to.

```
report-decision-framework/              # this repo, source of truth

```

## 3. Deployment model

The skill is not a separately maintained copy. `scripts/install.sh` symlinks it into the personal skills directory:

```bash
ln -s "$(pwd)/skill/report-decision-framework" ~/.claude/skills/report-decision-framework
```

A symlink, not a copy, so editing the repo edits what Claude Code loads, with no sync step and no drift between "the standard" and "what's installed." `git pull` on this repo updates the skill on every machine it's linked from.

## 4. Artifact schemas

### 4.1 `REPORT.md` (per project)
Generated by the existing `reporting` skill, extended to anchor every Concept, Implementation, and Experiment block: `### LSTM {#C1}`. Anchors are the only addition to that skill's output, the writing rules (density, no redundancy, definition/role/interaction order) are unchanged.

### 4.2 `DECISIONS.md` (per project)
Append-only. One entry per design decision:

```markdown
### D-20260916-LP-1 — Switch loss to focal loss
**Author:** Lluc Palou
**Date:** 2026-09-16
**Linked to:** C1, I1, E1
**Context:** [Empirical or requirement-driven justification.]
**Decision:** [What was decided.]
**Status:** Accepted, pending implementation | Implemented | Superseded by D-...
**Commits:** [hash (author), ...]
```

`Commits` starts empty, is appended to as work lands, and is a cache, never authoritative on its own.

### 4.3 Commit trailers
```
feat(I1): sliding-window feature extraction for OHLCV

Concept: I1, C1
Decision: D-20260916-LP-1
```
Parsed via `git log --format='%(trailers:key=Decision)'`. This is the canonical record; `DECISIONS.md`'s `Commits` field must always be a subset of what trailers show.

### 4.4 `CLAUDE.md` fragment
Instructs Claude Code to read `docs/REPORT.md` and `docs/DECISIONS.md` before implementation work, log a decision before writing code for it, and tag commits with both trailers.

### 4.5 `reconcile.py`
`--check`: scans `git log --all` for `Decision:` trailers, diffs against `DECISIONS.md`'s `Commits` fields, reports drift (non-zero exit, usable as a pre-push hook). `--fix`: rewrites the fields to match git. Idempotent either way.

## 5. ID grammar

| Form | Meaning | Collision risk |
|---|---|---|
| `C<n>`, `I<n>`, `E<n>` | Concept / Implementation / Experiment block in `REPORT.md` | None, single-document, sequential |
| `D-<YYYYMMDD>-<initials>-<n>` | Decision, dated, attributed, nth by that author that day | None, even across concurrent branches |
| `Concept:` trailer | Report block(s) a commit implements | n/a |
| `Decision:` trailer | Decision a commit executes | n/a |

## 6. Interaction model

```
E1 (experiment surfaces a finding)
  -> D-... (decision, justified by E1, linked to C1/I1)
      -> commits (trailers: Decision, Concept)
          -> REPORT.md block patched, only if the decision changed a claim,
             patch commit references the decision
```

`git log --grep=<ID>` on any ID, block or decision, returns the full causal trail with no separate database.

## 7. Framework versioning

Once this is used across multiple projects, the framework itself needs to change without silently reinterpreting old projects under a new schema. `SKILL.md` carries a semver (`version: 1.0.0`), `CHANGELOG.md` records what changed, and every project's `CLAUDE.md` fragment records which framework version it was scaffolded against. A schema change bumps the minor or major version and is a deliberate per-project migration, never a silent rewrite of existing `DECISIONS.md` files.

## 8. Per-project scaffold

Invoking the skill in a target repo creates, only where absent:
- `docs/REPORT.md` (from `REPORT.skeleton.md`, if no report exists yet)
- `docs/DECISIONS.md` (from `DECISIONS.skeleton.md`)
- `CLAUDE.md` (created, or `CLAUDE.fragment.md` appended if it already exists)
- `scripts/reconcile.py` (copied)
